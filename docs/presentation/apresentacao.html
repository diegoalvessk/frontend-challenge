1. Resumo do que foi entregue

A Kurio é um marketplace de NFTs com os fluxos completos de descoberta (catálogo com busca, filtros, ordenação e paginação), compra (detalhe, carrinho, pagamento com carteira e recibo) e conta do colecionador (cadastro, login, perfil, avatar, senha, carteiras e favoritos), em desktop e mobile, fiel ao Figma.

Não existe backend real: toda a API REST e o servidor de tempo real são simulados no navegador com MSW. Por isso a aplicação publicada funciona de ponta a ponta, inclusive os eventos Socket.IO, e qualquer cenário de falha pode ser reproduzido sob demanda.

3. Como foi construído

Stack — e o papel de cada peça

PeçaPapel na solução
TanStack RouterRotas por arquivo, parâmetros de busca validados com Zod (o estado do catálogo vive na URL) e guarda das rotas privadas
TanStack QueryCache por chave (isolado por usuário e por filtros), retries só para falhas transitórias, atualização otimista, invalidação após mutations e eventos
AxiosToda chamada REST: token, carrinho de visitante, normalização de erros e detecção de sessão expirada em um só lugar
Socket.IOnft.updated e order.updated com id estável e versão; deduplicação e reconciliação com REST
MSWAPI REST e servidor Socket.IO simulados no navegador, com estado persistente, cenários e reset
Tailwind + shadcn/uiTokens do Figma (cores, Roboto Mono) aplicados aos componentes Radix acessíveis (diálogos, drawers, abas, slider)
Zod + react-hook-formOs mesmos schemas validam o formulário e são revalidados pela API simulada
Playwright / LighthouseE2E, acessibilidade (axe), regressão visual e auditoria de performance

Camadas

UI (React + shadcn/ui) │ hooks por domínio (features/*) ◄── realtimeBus ◄── socket.io-client ▼ ▲ WebSocket TanStack Query (cache) ──► Axios ──► fetch/XHR │ │ │ ┌──────────── camada de mocks (MSW, no navegador) ─────────────────┴───────┐ │ handlers REST · servidor Socket.IO (socket.io-binding) │ │ domínio (carrinho, cotação, pedidos) · banco em localStorage · cenários│ └────────────────────────────────────────────────────────────────────────────┘

Contratos compartilhados: src/contracts define os tipos e schemas usados pela interface, pelo Axios e pelos mocks. Mudar um contrato quebra a compilação em todos os lados — é isso que garante "contratos tipados entre transporte, estado e interface".

Regra de ouro dos mocks: nenhum componente, hook ou o Axios contém dado fictício. A interface só conhece a rede; os testes e o painel de demonstração alteram o estado do servidor simulado, e a mudança chega pela resposta REST ou pelo evento.

Itens eliminatórios — todos evitados

  • Stack efetiva: cada tecnologia obrigatória participa do fluxo real (nada "instalado e não usado").
  • Fluxos não apenas visuais: toda ação passa pela API simulada e trata a resposta.
  • Compra só confirmada pela simulação: o recibo aparece apenas quando o servidor muda o pedido para confirmed.
  • Sem exposição entre usuários: cache por usuário, socket por sessão, filtro de eventos no servidor e no cliente, 403 em pedido alheio.
  • Eventos não simulados na UI: chegam pelo socket.io-client, vindos do servidor MSW.
  • E2E executáveis: npm run test:e2e a partir de um checkout limpo.

5. Os pontos mais delicados — e como foram resolvidos

Compra sem pedido duplicado (idempotência)

  • Cada tentativa de compra recebe uma chave de idempotência, salva junto com o corpo enviado.
  • Se a resposta demora (timeout) ou a rede cai, o app reenvia com a mesma chave: o servidor devolve o mesmo pedido. Cliques repetidos são ignorados enquanto há envio em andamento.
  • Mesma chave com conteúdo diferente → 409 IDEMPOTENCY_CONFLICT.
  • Pedido pendente sobrevive a refresh: a página do pedido consulta o REST, ouve order.updated e faz polling de segurança.

Preço mudou durante a compra (cenário exigido)

  1. Um NFT está no carrinho.
  2. O servidor altera o preço e publica nft.updated.
  3. O carrinho mostra "Preço alterado de X para Y", o resumo é recalculado pela API e o checkout informa as mudanças.
  4. O botão de confirmar fica bloqueado até "Revisar novos valores". Se mesmo assim uma cotação velha chegar ao servidor, ele responde 409 QUOTE_STALE com a nova cotação.

Sessão expirada no meio do caminho

Qualquer 401 encerra a sessão local; em rota privada o usuário vai ao login com ?redirect= e volta ao mesmo ponto. O formulário de pagamento é salvo continuamente e restaurado. Logout e troca de usuário limpam o cache privado e encerram o socket da sessão anterior.

Valores em ETH sem erro de arredondamento

Valores trafegam como strings decimais e são calculados com decimal.js (ex.: 2.78 − 0.278 + 0.016 = 2.518 exatos). O recibo é um snapshot: mudanças posteriores no catálogo não alteram o pedido.

Respostas fora de ordem

Cada combinação de filtros tem sua própria chave de cache e a requisição anterior é cancelada; com latência variável, o grid sempre corresponde aos filtros finais (há teste para isso).

O que foi feito para chegar lá

  • Imagens: artes de ~2 MB do Figma viraram WebP responsivo de 11–48 KB, com dimensões reservadas (sem saltos de layout) e lazy loading fora da tela.
  • LCP: a arte do banner é pré-carregada no HTML e o banner não depende da API.
  • Bundle dos mocks 3× menor: uma dependência do MSW (tough-cookie) embutia uma lista de domínios de ~120 KB que a aplicação não usa; foi trocada por um substituto mínimo. A performance mobile foi de 84 para 91.
  • Decisões medidas: testei baixar mocks e aplicação em paralelo, mas no 4G simulado isso piorou o LCP; a ordem sequencial foi mantida com base na medição.
  • Fonte pré-carregada: eliminou o deslocamento de layout causado pela troca tardia da fonte.
  • CLS: skeletons com as dimensões finais; seções secundárias só aparecem após o conteúdo principal.
  • Code splitting por rota e fonte servida localmente.
Ponto honesto para a apresentação: parte do custo de carregamento no mobile vem da própria API simulada (MSW, fixtures e handlers, ~54 KB comprimidos), que em produção com backend real não existiria. Ela foi mantida na auditoria porque o enunciado pede medir a entrega real, sem simplificações só para a nota.

8. Roteiro de demonstração (~10 minutos)

  1. Catálogo (1 min). Na home, filtre por "Música" + "Ethereum", ordene por menor preço e vá à página 2. Recarregue a página e use o botão voltar: o estado é mantido. Mostre o painel "Mocks" → "Rede lenta" para os skeletons.
  2. Detalhe (1 min). Abra "Sage Nomad #009": a edição 1/1 está esgotada e não pode ser escolhida; aumente a quantidade até o limite. Acesse /nft/nao-existe para o 404.
  3. Carrinho como visitante (1 min). Adicione dois NFTs, aplique VERAO2025 (expirado), depois KURIO10. Mostre que o total vem da API.
  4. Login e retorno ao fluxo (1 min). "Conectar e finalizar" → login com ana@kurio.dev / Kurio@2026 → volta direto ao pagamento, com os itens do visitante preservados.
  5. Tempo real no checkout (2 min). No pagamento, abra o painel → "Subir preço do 1º item do carrinho". O aviso aparece e o botão de confirmar é bloqueado. Clique em "Revisar novos valores".
  6. Compra (1 min). "Confirmar compra" → a carteira conecta → revisão → confirmar. Mostre o estado pendente e o recibo chegando via order.updated.
  7. Falhas de pagamento (2 min). Painel → "Timeout no pedido" e compre de novo: após ~8 s o app reenvia com a mesma chave e abre o mesmo pedido. Depois "Pagamento recusado": os itens continuam no carrinho.
  8. Conta (1 min). Perfil: troque o avatar, tente usar o usuário bruno.holder (conflito). Carteiras: cadastre a secundária "igual à principal". Painel → "Expirar sessão agora" e navegue.
Se algo sair do esperado durante a demonstração, use o painel "Mocks" → "Resetar todos os dados" para voltar ao estado inicial conhecido.

9. Decisões, desvios do Figma e limitações

  • Login/cadastro como diálogo sobre a home (Figma); em tela cheia no mobile.
  • Funcionalidades fora do escopo (login social, recuperar senha, newsletter, Criadores, Aprenda, Atividade, Ofertas, Suporte) mostram que não estão disponíveis — nunca simulam sucesso.
  • Telas sem frame (pedido pendente/recusado, revisão do pedido, favoritos, estados de erro/vazio) seguem a mesma identidade visual.
  • Galeria: o Figma repete a mesma imagem nas miniaturas; viraram 4 vistas (obra inteira e detalhes).
  • Pagamento: une a proposta do desktop (formulário) e do mobile (cartões de carteira) em todas as larguras.
  • Limitações: blockchain, carteiras e pagamentos são simulados; os dados ficam no navegador de cada visitante; baselines visuais geradas no Windows.

10. Perguntas prováveis

Por que os mocks rodam no navegador e não num servidor?
O enunciado pede MSW e deploy estático funcionando com mocks e tempo real. Rodar no navegador garante que a URL publicada funcione sem infraestrutura, e os mesmos handlers servem desenvolvimento, demonstração e testes.
Como os eventos Socket.IO funcionam sem servidor?
O MSW intercepta o WebSocket aberto pelo socket.io-client e o @mswjs/socket.io-binding fala o protocolo Socket.IO. Detalhe técnico: o engine.io guarda o construtor de WebSocket ao carregar, então o cliente Socket.IO só é importado depois que o MSW inicia.
Como você evita mostrar dados de um usuário para outro?
Chaves de cache com o id do usuário, limpeza do cache no logout/troca, um socket por sessão autenticado pelo token, filtro de order.updated no servidor e conferência do userId no cliente, além de 403 para pedidos de outra conta.
Onde está a atualização otimista?
Nos favoritos: a interface muda na hora; se a API falhar (cenário favorites-fail), volta ao estado anterior e avisa.
O que você faria com mais tempo?
Separar a camada de mocks do bundle de produção num build dedicado de demonstração, adicionar testes de contrato e um backend real atrás dos mesmos contratos.
